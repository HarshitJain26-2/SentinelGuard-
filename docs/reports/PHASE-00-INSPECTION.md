## 11. Why `extension/` Is the Correct Member 1 Location

Several alternative locations were considered and rejected:

| Alternative | Reason Rejected |
|-------------|-----------------|
| `src/extension/` | Unnecessary nesting; Chrome extensions have no standardized `src/` wrapper |
| `frontend/extension/` | Misleading — browser extensions are not traditional "frontends"; they are autonomous browser programs |
| Root-level `manifest.json` | Would pollute the repo root; multiple members' top-level files would conflict |
| Inside `backend/static/` | Extensions are not Django static assets; coupling them to the backend creates a deployment dependency |

`extension/` at the repository root is:
- Conventional for multi-component repos with a browser extension as one component
- Self-contained — the extension can be loaded directly into Chrome from this path
- Clearly bounded — no ambiguity about what belongs in this folder
- Conflict-free — other members have no reason to touch this directory

## 12. Why API Contract Coordination Is Required

The browser extension (Member 1) and the Django backend (Member 2) are **tightly coupled at their interface boundary**. Member 1 produces a JSON payload; Member 2 must consume it. If these are not aligned:

- Member 1's extension will POST data that Member 2's API rejects (400 errors).
- Member 2's feature engineering will expect fields that Member 1 never sends.
- Member 1's privacy guarantees (no key values) must be reflected in Member 2's API design — Member 2 must not design API fields that would require Member 1 to send prohibited data.

The [`DATA_SCHEMA.md`](../DATA_SCHEMA.md) document exists specifically to make this coordination artifact explicit and version-controlled. The sign-off block in that document is the formal gate before integration work begins.

---

## 13. Why Privacy Requirements Matter

The browser extension occupies a **uniquely privileged position**: it runs inside the user's browser, observes their keystrokes and mouse movements on login forms, and transmits data to a server. Without explicit, documented privacy constraints:

- Developers might accidentally include key values in timing logs (catastrophic credential leak).
- The extension might read password field `.value` during debugging and commit that code.
- Users have no way to know what is being collected or opt out.

The [`PRIVACY.md`](../PRIVACY.md) document exists because these are not abstract concerns — they are real failure modes that have occurred in commercial browser extensions. Making the constraints explicit, version-controlled, and binding before any implementation begins is the safest engineering practice.

The ON/OFF toggle requirement exists because:
- User transparency is a fundamental design principle.
- Without it, the extension is indistinguishable from spyware from the user's perspective.
- GDPR, CCPA, and similar regulations effectively require this control even for behavioral metadata.
